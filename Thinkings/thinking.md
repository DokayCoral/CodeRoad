[Claude Code 概述 - Claude Code Docs](https://code.claude.com/docs/zh-CN/overview)

给Claude一种验证其工作的方式。软件描述的工具让Claude知道自己该做什么，软件验证的工具让Claude知道自己做得对不对。

先探索，再规划，最后编码。对于范围明确且修复很小的任务（如修复拼写错误、添加日志行或重命名变量），要求 Claude 直接执行。当你对方法不确定、更改修改多个文件或你不熟悉被修改的代码时，规划最有用。如果你能用一句话描述 diff，跳过计划。

配置好项目环境。运行 `/init` 根据当前项目结构生成启动 CLAUDE.md 文件，然后随时间精化。CLAUDE.md 是一个特殊文件，Claude 在每次对话开始时读取。包括 Bash 命令、代码风格和工作流规则。这给 Claude 提供了它无法从代码中推断的持久上下文。CLAUDE.md 在每个会话中加载，所以只包括广泛适用的东西。对于仅有时相关的域知识或工作流，改用 [skills](https://code.claude.com/docs/zh-CN/skills)。Claude 按需加载它们，不会使每次对话都膨胀。保持简洁。对于每一行，问自己：*“删除这个会导致 Claude 犯错吗？”* 如果不会，删除它。膨胀的 CLAUDE.md 文件会导致 Claude 忽略你的实际指令！

像对待代码一样对待 CLAUDE.md：当事情出错时审查它，定期修剪它，并通过观察 Claude 的行为是否实际改变来测试更改。这个部分是人应该发挥作用的部分。

要使用CLI、MCP、Skills、Hooks、subagents、plugins。

[理解规范驱动开发：Kiro、spec-kit和Tessl - InfoQ](https://www.infoq.cn/article/4GT6jbMzEmCBavfDlzHK)

一个有效的 SDD 工具必须提供非常好的规范审查体验。

过去的经验已经表明，我们保持对正在构建的内容的控制的最佳方式是一系列小的、迭代的步骤，所以我非常怀疑大量的前期规范设计是否是个好主意，特别是当它过于冗长时。一个有效的 SDD 工具必须迎合迭代方法，但小的工作包几乎似乎与 SDD 的理念相悖。

在 SDD 中，有意识地区分功能规范和技术实现是一个常见的想法。我猜背后的愿景是，最终，我们可以有 AI 填充所有的解决方案和细节，并在相同的规范下切换到不同的技术栈。

## 方法论

按照传统软件工程思路，我们把软件开发分为四个部分：1. 软件描述；2. 软件开发；3. 软件测试；4. 软件进化。针对各个流程，把现有的工具和AI结合，可以把AI开发流程工程化。抽象地说，就是人类设计和监督流程，AI执行流程。

软件描述：1. 确定需求管理工具（需要有自己对开发工具的知识存储与深刻认识）；2. 让AI工具可以使用需求管理工具（在这一步我们也可以看到，AI软开思想应该收敛到一切行为无工具的程度。）；3.  确定需求管理的流程。这一步需要结合传统软件工程的需求管理思想，要存储各种需求管理的情况，需求管理的流程应该以可插拔的形式存储在文件中，这也许是未来个人的资产、公司的资产。我们先使用Pingcode试一试。

软件开发：软件开发过程要求参与人员有：传统程序员对代码业务的深刻理解和新时代程序员对AI工具的深刻认识和高效使用。

软件测试：软件测试过程要做到覆盖软件描述，测试的内容要大于等于业务的需求。我们需要可以同时整合需求和测试的工具。如果没有这种工具，我们就需要手动统一这个流程。

软件进化：软件进化不止是业务代码的进化，还包括了对AI使用方法的进化。一个项目可能有特殊的流程适合最优的开发，那么对应着就应该有一个特殊的AI使用方法。这就要求我们对AI软件开发过程要有一个适应性强的基础模板方法，在基础模板方法的基础上要有进化机制，使得可以”与时俱进“。

额外的，日志是一个重要的细节。在这里我们指的是开发日志，使得我们可以更加标准地管理开发过程。那么我们要记录什么信息？

### 怎么确定验证的过程呢？

Spec-Kit中，为每个task创建了验证脚本。问题在于，如何确保验证过程也是可控的呢？换句话说，把测试过程也委托AI，出现在开发过程的错误怎么就不会出现在测试过程中。

### 第一次开发中出现的问题：

1. 首页不干净，我们启动时最好清空控制台的所有消息，只保留系统的信息。
2. 第一次没有配置API_KEY就直接报错退出，用户体验不好。
3. API_KEY还有一个问题，我们使用的是DeepSeek的代理，并没有使用Claude模型。所以我们应该按照DeepSeek的环境变量要求去设计。[Anthropic API | DeepSeek API Docs](https://api-docs.deepseek.com/zh-cn/guides/anthropic_api)对相关细节有所描述。

针对这三个问题，我们使用specify来更新需求。在使用过程我们发现，对于明确需求，我们可以跳过clarify，直接进行plan。

如果针对每个问题都使用specify，那么每次都会开一个新的需求，这太过冗余。我们应该针对性地识别每个需求，分成层次，分成条块。这样便于我们对需求进行管理。也可以一定程度上解决需求漂移、项目理解的问题。

那么，Spec-Kit目前看来就更合适于原型开发，这样的话，需求是低耦合地按块管理，更加方便。

目前我们使用的是另一种方法，001-spec是顶层、最全面的需求，后续的需求是对001不足的改进。

如果是修bug，那么可以直接和cc交流，不使用spec kit。

## 如何量化我们的开发过程？

1. 时间

同下。用少的时间、少的token开发出最”正确“的软件。

2. 资金

用更好的模型，可以用更少的toekn。任务规划的复杂程度和业务的正确程度是一组trade-off。Spec-Kit是一种思想的实现，但不是银弹。在使用superpowers的过程中，出现了实现过程过于复杂的问题。总的来说，一定要对业务的复杂程度有一个正确的估计，根据估计来选择合适的工具。简单的业务应该用简单的工具，复杂的业务应该用复杂的工具。

用更好的Agent工具，也可以用更少的Token。
